## A. Баги: интерфейс говорит неправду

### A1. Задача отчитывается «готово» при полном провале — P0

`drydock/server.py:293` (`_failed_count`), `:329` (`_job_state`).

`_job_state` считает провалом только ключи `failed`, `cloud_failed`,
`linked_failed`, `no_space`. А `download.run` (`download.py:535`) и
`probe.run` возвращают **счётчики по состояниям**: `ok`, `unavailable`,
`gone`, `api_error`, `mismatch`. Ключа `failed` там нет вообще.

Замер (реальный вызов):

```
выгрузка 5 ok / 100 недоступно -> done
выгрузка 0 ok / 6324 недоступно -> done
проба 0 ok / 500 bad -> done
круг (run_rounds) -> done
```

То есть «Скачать выбранное», где не скачался ни один файл, показывает зелёное
«готово». В подвале из-за этого занижается счётчик `✕` — он считается по
состояниям задач.

Ирония: функция написана ровно против этого («задача #46 отчиталась done с
failed=140»), но проверяет словарь другой формы.

**Починить.** Либо `download.run`/`probe.run` добавляют в результат
`"failed": сумма неуспешных состояний`, либо `_failed_count` знает словарь
состояний (`unavailable`, `gone`, `api_error`, `unknown`, `mismatch`,
`no_space`). Второе честнее: форма результата у всех работ разная, а
«провал» — понятие общее.

**Проверить.** Тест: `_job_state({"ok": 0, "unavailable": 10})` → `failed`,
`_job_state({"ok": 5, "unavailable": 10})` → `partial`.

### A2. Круг не замечает полный диск и молотит вхолостую — P0

`drydock/download.py:463` (`run_rounds`), `:531` (возврат).

`run()` внутри круга видит `no_space` и останавливает порцию, но `run_rounds`
читает из результата только `ok` и `cancelled`:

```python
got = int(res.get("ok", 0) or 0)
...
if got == 0:
    await nap(pause_s)      # 60 секунд
```

Дальше очередь пересобирается (файлы никуда не делись), снова `no_space`,
снова `got == 0`, снова пауза. Полный диск = бесконечные круги раз в минуту,
без единого сообщения о причине. И задача при остановке отчитается «готово»
(см. A1), потому что `no_space` в результат круга не попадает.

**Починить.** Пробрасывать `no_space` из `run()` в результат `run_rounds` и
выходить из цикла с внятным сообщением («диск полон, освободите место»).

**Проверить.** Тест: `run` с подменённым `free_space` → `run_rounds` делает
один круг и возвращает `no_space: 1`.

### A3. Линза «На диске» показывает файлы без объёма — P1

`web/app.js:137` (`lensOf`), `drydock/tree.py:131`.

```js
if (LENS === "disk") return { files: node.present || 0, bytes: node.saved_bytes || 0 };
```

`present` — любая годная копия (включая `unverified` и `salvaged`),
`saved_bytes` — только `verify='ok'`. Для папки, которую перенесли вручную,
получается «2 092 шт · 0 Б»:

```
папка, перенесённая вручную: present 2092 | saved_bytes 0.0 МБ
1_семестр  present  211 | saved_bytes 548.5 МБ
```

**Починить.** Считать байты тем же правилом, что и штуки: `present_bytes`
(ok + unverified + salvaged).

### A4. Число на кнопке «Круг» и очередь задачи считаются по-разному — P2

`web/app.js:264` (`paintActions`) берёт `remaining.by_state.unavailable`,
а задача берёт `download.pending_targets()` — там ещё `unchecked`,
`api_error`, `unknown` и отлёжка после провала.

Замер: кнопка 677, очередь 681. Расхождение небольшое, но правило разное,
поэтому оно будет плавать в обе стороны (раньше было 682 против 660).

**Починить.** Один источник: отдавать в `/api/state` результат
`download.pending_targets()` (или его счётчик) и показывать его.

## B. Ошибки, которые проявятся позже

### B1. Кавычки не экранируются, а `esc()` используется в атрибутах — P1

`web/app.js:12`:

```js
const esc = (s) => String(s).replace(/&/g, "&amp;").replace(/</g, "&lt;");
```

Ни `"`, ни `'`, ни `>` не экранируются. Для текста внутри `innerHTML` этого
достаточно, но `esc()` подставляется и в атрибуты:
`title="${esc(x.host)}"`, `title="${esc(x.path)}"` и т. п.

Проверка:

```
esc('x" onmouseover="alert(1)')  ->  x" onmouseover="alert(1)
```

Имена файлов приходят из облака, то есть контролируются не нами. Сейчас это
ломает разметку, при неаккуратном имени — даёт исполняемый атрибут.

Рядом уже лежит правильная функция `attrEsc` (`app.js:870`), но применяется
в одном месте.

**Починить.** Один `esc()` экранирует все пять символов, либо везде в
атрибутах — `attrEsc`.

### B2. Апостроф в пути ломает кнопку «открыть папку» — P1

`web/app.js:881`:

```js
`<button class="ghost" onclick="revealFile('${encodeURIComponent(path)}')">`
```

`encodeURIComponent` **не кодирует апостроф**:

```
encodeURIComponent("O'Brien.docx") -> O'Brien.docx
```

Итог: `onclick="revealFile('O'Brien.docx')"` — синтаксическая ошибка, кнопка
не работает. То же в `hostsModal` (`:1078`), но там имя узла — DNS-метка,
апострофа быть не может.

**Починить.** Не собирать обработчики строками: вешать `onclick` на элемент
после вставки (как уже сделано для `tryHost` через `window.`), либо
`JSON.stringify` + экранирование кавычек.

### B3. В запросе строк дерева две колонки объявлены дважды — P1

`drydock/tree.py:115-135`. Ветка `full=False, extra=True` добавляет
`live_bytes` и `missing_local`, которые уже есть в `common`.

Замер по тексту запроса:

```
колонок: 21 | повторы: {'live_bytes': 2, 'missing_local': 2}
```

SQLite молча берёт первую, поэтому сейчас это только лишняя работа. Но две
формулы одного числа — это две правды: поправят одну, а читаться будет
другая.

**Починить.** Убрать дубли из ветки `extra`, оставить только `saved_bytes`.

### B4. Общее соединение и `BEGIN` в чужом потоке — P1

`drydock/localwatch.py:136`. Одно соединение на весь процесс
(`check_same_thread=False`), `BEGIN…COMMIT` выполняется внутри
`asyncio.to_thread`. Замок `_LOCK` сериализует только саму сверку, но не
защищает от записи из петли событий в это же окно: `record_probe`,
`job_progress`, `save_local` попадут внутрь чужой транзакции и откатятся
вместе с ней. Комментарий в файле это признаёт («cannot start a transaction
within a transaction»), но лечит только половину случая.

**Починить.** Либо соединение на поток (или пул), либо `BEGIN IMMEDIATE` под
общим мьютексом, который берут все писатели.

### B5. `unchecked` и `ok` не исключают удалённое нами — P2

`drydock/tree.py:66-72`: `ok` и `unchecked` не проверяют
`cloud_deleted`, тогда как `unavailable` и `gone` — проверяют. Спасает
разовый `_repair_deleted_probe` при старте, но если файл удалили из облака
мимо `cloud.delete` или ремонт не отработал, он вернётся в «доступно».

**Починить.** Добавить `cd.path IS NULL` во все ветки — единообразно.

### B6. Поиск: `%` и `_` в запросе работают как шаблоны — P2

`drydock/server.py` (`search`): `r.name LIKE ?` с `f"%{q}%"`. Ввод `%`
вернёт всю коллекцию (до лимита), `_` совпадёт с любым символом. Инъекции нет
(параметр), но поведение неожиданное.

**Починить.** Экранировать `%`, `_`, `\` и добавить `ESCAPE '\'`.

### B7. `state()` меняет закэшированный словарь — P2

`drydock/server.py:459+`: `totals = cached_totals(...)`, затем
`totals["free_pct"] = ...`. Это тот же объект, что лежит в кэше. Если
`shutil.disk_usage` бросит `OSError`, в кэше останется `free_pct` от прошлого
раза — и совет «пора архивировать» будет опираться на устаревшее место.

**Починить.** Копия перед изменением: `totals = dict(cached_totals(...))`.

### B8. Оценка времени круга — константа 20 с/файл — P2

`drydock/server.py:488`: `"hours": round(unavail * 20 / 3600, 1)`.
Замеры в разное время давали 2 с/файл (быстрая выборка) и 23.5 с/файл
(полный проход). Число в интерфейсе — «Прогон займёт около N ч» — будет
врать тем сильнее, чем больше отличается реальный темп.

**Починить.** Считать по последним завершённым кругам (в `jobs` есть
`started_at`/`finished_at`/`done`), а константу оставить запасным вариантом.

## F. Узкие места на нашей стороне

### F1. `/api/state` — 587 мс, опрашивается каждые 5 с — P1

```
/api/state            587 мс
  totals              511 мс   (кэш 10 с)
  remaining            46 мс

```

`totals` — это ~30 агрегатов по 26 тыс. строк с четырьмя соединениями. При
TTL 10 с и опросе раз в 5 с каждая вторая выборка платит полсекунды, и всё
это на том же соединении, куда пишет выгрузка. Пока идёт круг, это ещё и
конкуренция за блокировку SQLite.

**Что делать.** Считать только те ~15 полей, которые интерфейс реально
показывает (сейчас считаются все); либо держать сводку в отдельной таблице,
обновляемой пачками после записи.

### F2. `/api/health` — 522 мс, и это без индексов — P1

`health.report` группирует `probe_history` по дате (115 тыс. строк),
`local` по `downloaded_at`, `cloud_deleted` по `deleted_at`, `jobs` по
`started_at`. Индексов нет ни на одном из этих полей:

```
ix_res_parent, ix_res_type, ix_probe_state, ix_ph_path(path, ts),
ix_local_verify, ix_am_path, ix_am_arch, ix_res_vanished
```

`ix_ph_path` начинается с `path`, поэтому группировка по `ts` его не
использует.

**Что делать.** Три индекса: `probe_history(ts)`, `local(downloaded_at)`,
`cloud_deleted(deleted_at)`, `jobs(started_at)`. Ожидаемо — десятки
миллисекунд вместо полусекунды.

### F3. N+1 при раскрытии папки — P2

`tree.py:183-230`: после общего запроса по папке идёт **отдельный запрос на
каждый файл** (`detail = conn.execute(...)` внутри цикла).

Замер: папка с 615 файлами — 35 мс (то есть ~0.05 мс на запрос, prepared
statement спасает). Сейчас терпимо, но растёт линейно: 5 000 файлов в одной
папке — это 5 000 запросов и сотни миллисекунд.

**Что делать.** Присоединить `meta_saved` и поля `local` в основной запрос
(они уже есть в `JOINS`), либо один `SELECT ... WHERE path IN (...)` на всю
страницу.

### F4. `probe_history` растёт без ограничения — P2

115 486 строк сейчас, +26 тыс. за полный проход пробы. Чистки нет: в коде
единственный `DELETE FROM` — это `kv_del`. Через год это миллионы строк,
и F2 станет хуже.

**Что делать.** Хранить историю N дней (или последние K записей на путь) и
чистить при старте.

### F5. Опрос задач каждые 1.5 с даже в простое — P3

**Что делать.** В простое — раз в 10–15 с, при активной задаче — как сейчас.

### F6. Четыре запроса плана на каждое изменение выбора — P3
